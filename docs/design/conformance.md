# Conformance strategy

sigillum demonstrates conformance in two ways: mechanically, by differential testing against DSS, and externally, through ETSI test events and independent review. Agreement with DSS is necessary but not sufficient; trust is earned through external evidence over time.

## DSS as an oracle

DSS is used as a black box for testing. It runs as a separate process (a pinned release of its validation web service or command-line demonstration), receives signed objects, and returns its reports. It is never linked into sigillum, and no DSS code or test data is included in the repository ([ADR-0004](adr/0004-dss-as-test-oracle.md)).

Every comparison runs with:

- a **fixed validation time**, so results do not change with the calendar;
- **offline sources** for certificates, OCSP responses, CRLs and timestamps, so both implementations see identical inputs;
- a **pinned DSS release**, upgraded deliberately, with any change in results reviewed.

## Three seams

DSS separates the extraction of facts from a signed object (its diagnostic data) from the validation logic that reasons over those facts and a policy. This gives three layers that can be tested independently.

1. **Creation.** Every signature sigillum produces is submitted to DSS and must obtain the expected indication. Byte-level identity with DSS output is not required; structural and semantic equivalence is.
2. **Extraction.** For a given signed object, sigillum's description of what it contains (signers, certificates, references, timestamps, revocation data) is compared field by field with DSS diagnostic data.
3. **Validation logic.** Phase 3's engine consumes DSS diagnostic data and must reproduce the indication, sub-indication and per-constraint results of the DSS reports.

## Test corpus

| Source | Content | Licensing note |
| --- | --- | --- |
| Project test PKI | Root and issuing CAs, OCSP responder, CRLs, timestamping authority, with valid, expired, revoked and misconfigured certificates | Generated by the project, freely redistributable |
| Generated signatures | Every supported format and level, valid and deliberately broken variants | Generated by the project |
| Public samples | Signed documents from public sources where redistribution is permitted | Included only with a recorded licence |
| Fuzzing | Mutants of the above, generated continuously | Generated by the project |

Real signed documents containing personal data are never added to the corpus.

## Fuzzing

Every parser (ASN.1 structures, CMS, PDF objects and cross-reference sections, OCSP, CRL, timestamp tokens) has a `cargo-fuzz` target. Fuzz targets check for crashes and, where a reference result exists, for divergence from DSS on inputs that DSS accepts.

## Recording divergences

Where sigillum intentionally behaves differently from DSS, because the ETSI text requires it or because DSS behaviour appears incorrect, the case is recorded in [divergences.md](divergences.md) with the clause of the standard concerned, a test vector, and a link to the report made to the DSS maintainers. An unrecorded divergence is a defect.

## External evidence

- Structural checks of produced signatures with the ETSI signatures conformance checker.
- Participation in ETSI remote signature plugtests from phase 3.
- Conformance testing against the ETSI test specifications for each format (TS 119 124 for CAdES, TS 119 144 for PAdES).
- An independent security review before any verification feature is declared stable.
