# ADR-0015: Implement a minimal PDF reader and an incremental-update writer

- **Status:** Accepted
- **Date:** 2026-10-23
- **Issue:** #19

## Context

PAdES signing appends an incremental update to the PDF document (ISO 32000-1:2008, clause 7.5.6). The update contains a signature dictionary whose `ByteRange` covers the whole file except the signature value. At B-LT it also contains a document security store holding validation data (ETSI EN 319 142-1 V1.2.1). Verification must detect changes made after signing, including the shadow and incremental-save attacks published against PDF signatures since 2019.

Signing needs exact control over every byte written. Verification needs a parser that is strict about structure, tolerant of the irregularities common in real documents, and safe on hostile input. `lopdf` supports incremental updates since version 0.29, but it is a general-purpose library. It is not designed for hostile input and does not expose the byte-level layout that the `ByteRange` depends on. It also has no model of the revision chain that verification needs.

## Decision

A new crate, `sigillum-pdf`, provides:

- a minimal reader for the structures signatures need: header, cross-reference tables and streams, trailers, the revision chain, indirect objects on demand, the document catalogue, AcroForm fields and signature dictionaries;
- an append-only incremental-update writer that computes the `ByteRange`, reserves and fills the signature contents, and writes the document security store;
- a revision analysis used by verification to report what changed after each signature.

Generation of the visible appearance stream belongs to `sigillum-pades`, which uses the writer of `sigillum-pdf`. Rendering, and modification detection that requires rendering, are out of scope ([scope.md](../../project/scope.md)). `lopdf` may be used in tests as an independent second parser to cross-check the reader, but not in library code.

## Alternatives considered

| Option | Advantages | Disadvantages |
| --- | --- | --- |
| `lopdf` for reading and incremental writing | Ready-made, incremental updates supported | Not designed for hostile input; no byte-level layout control; no revision model |
| `lopdf` for reading, own writer | Less code | Two models of the same document; parser not designed for hostile input |
| Own minimal reader and incremental writer | Exact byte control; small, fuzzable surface; revision model built in | More code to write and fuzz |

## Consequences

`sigillum-pdf` is a critical module: every parser entry point has a fuzz target, and the mutation-testing threshold applies. The corpus includes PDF files that exercise known incremental-update attacks, generated by the project.
