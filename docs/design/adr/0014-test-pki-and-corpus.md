# ADR-0014: Generate the test PKI and corpus, and verify them independently

- **Status:** Accepted
- **Date:** 2026-10-23
- **Issue:** #19

## Context

Tests need certificates, CRLs, OCSP responses and timestamp tokens covering valid, expired, not yet valid, revoked, misconfigured and malformed cases, and signed documents built on them. Real certificates and signed documents cannot be used: they expire, they may contain personal data, and their licences are unknown. Every time field must be tied to one fixed validation time, so that expired and not-yet-valid cases stay stable. Fixtures that were never checked by an implementation other than sigillum's could hide an encoding defect shared by the generator and the code under test.

## Decision

A dedicated, unpublished crate, `sigillum-testpki`, generates every PKI artefact and the unsigned base documents in Rust:

- `rcgen` for certificates and CRLs signed with algorithms it supports;
- the `x509-cert` certificate builder for certificates that `rcgen` cannot produce, such as those signed with RSASSA-PSS, SHA-3 or P-521;
- `x509-cert` CRL structures, signed by the generator, for CRLs that `rcgen` cannot produce, because `x509-cert` 0.2 has no CRL builder;
- the `cms` SignedData builder for timestamp tokens, as SignedData over TSTInfo (RFC 3161);
- the `x509-ocsp` response builder for OCSP responses (RFC 6960).

The choice of tools for certificates is changed by [ADR-0021](0021-x509-cert-builder-for-test-certificates.md), and for CRLs by [ADR-0022](0022-x509-cert-structures-for-test-crls.md).

Every time field (`notBefore`, `notAfter`, `thisUpdate`, `nextUpdate`, `producedAt`, `genTime`) is set explicitly from the fixed validation time. Where a primitive crate does not supply the algorithm identifier, as for P-521 and for SHA-3 with RSA PKCS#1 v1.5 or ECDSA, the generator uses a small signer wrapper. Timestamp tokens carry no signing-time attribute taken from the system clock, and the ESS signing-certificate attribute that RFC 3161 requires is built by the generator.

Signed documents are not produced by sigillum's crates. They are generated by DSS through the `sign` mode of `tools/dss-oracle` ([ADR-0013](0013-dss-oracle-command-line-tool.md)), with test PKI keys and a fixed signing time. Malformed signed documents, such as PDF incremental-save and shadow variants or tampered JAdES headers, are produced by `sigillum-testpki` by mutating DSS-generated documents. `sigillum-testpki` is not part of the library and may use `lopdf` for PDF mutations; [ADR-0015](0015-pdf-reader-and-incremental-writer.md) governs the PDF handling of the library only. The unsigned base documents are generated by `sigillum-testpki`. These fixtures feed the extraction seam (2) of [conformance.md](../conformance.md), alongside the creation seam (1).

`sigillum-testpki` is a command-line program. One subcommand issues timestamp tokens for the `sign` mode of `tools/dss-oracle`; `sigillum-testpki verify` runs the fixture checks.

Independence comes from verification, not from generation. The generator shares crates with the code under test, so continuous integration checks every PKI artefact and every CAdES fixture with two independent implementations:

- OpenSSL checks every PKI artefact (certificates, CRLs, OCSP responses, timestamp tokens) and the CAdES fixtures, through `openssl cms -verify`. It cannot check PAdES or JAdES;
- DSS checks every PKI artefact, through its `validate-certificate` and `validate-timestamp` modes, and every signed document;
- every artefact must match the results recorded in its manifest, which for malformed artefacts is a rejection or a specific sub-indication.

An artefact that fails this check blocks the build. PAdES and JAdES fixtures are checked only by DSS, which generated them. Their independent reader is sigillum itself, through the extraction seam, and any disagreement is investigated before the fixture is accepted.

The generated artefacts are committed under `testdata/`, with a manifest that records each artefact's purpose and the results expected from OpenSSL and DSS. Regeneration is an explicit step, not part of every build. Byte-for-byte reproducibility is not required, because ECDSA signatures are randomised.

External test suites without a clear licence, such as NIST PKITS, are not committed. They are downloaded at test time and checked against a recorded digest.

## Alternatives considered

| Option | Advantages | Disadvantages |
| --- | --- | --- |
| Shell scripts around OpenSSL only | Simple; independent of the code under test | Cannot set `producedAt`, `thisUpdate` or `genTime`; hard to maintain; weak handling of edge cases such as malformed extensions |
| OpenSSL under `libfaketime` | Fixed times without code | Fragile; limited on macOS by System Integrity Protection; hides time handling outside the code |
| Bouncy Castle generator in Java | Mature; every time field settable | A second Java tool to maintain; DSS itself uses Bouncy Castle, so it is not independent of the oracle |
| Generator without independent verification | One code base, no external checks | Fixtures share the defects of the code under test, unseen |
| Rust generator, verified by OpenSSL and DSS | One language; every time field set in code; edge cases expressible in code; two independent checks | Generator and code under test share crates; OpenSSL to pin in CI |

## Consequences

The test PKI is the first deliverable of phase 0, because the differential harness has nothing to compare without it. Malformed variants are generated by mutating valid artefacts in the generator, and are recorded in the manifest like any other artefact.

The generator signs with RSA private keys. [ADR-0010](0010-cryptographic-backend.md) allows this in `sigillum-testpki`, because timing attacks do not apply to test keys.

Two residual risks remain. A defect shared by the generator, OpenSSL and DSS would go unnoticed. A defect in DSS signing would reach the PAdES and JAdES fixtures, checked only by DSS. NIST PKITS and public samples with recorded licences, produced by other implementations, reduce both.
