# ADR-0024: Bounded decoding of untrusted input

- **Status:** Accepted; move of `check_der` to `sigillum-pki` superseded by [ADR-0025](0025-build-phase-1-on-der-0-8.md)
- **Date:** 2026-10-25
- **Issue:** #78

## Context

The library crates decode untrusted input: certificates, CRLs, OCSP responses, timestamp tokens and CMS structures. This input crosses boundaries B1 and B2 of the [threat model](../threat-model.md). Threat P2 requires explicit limits on declared sizes and nesting depth. Objective O3 requires that no input can make the library panic or consume unbounded memory.

[ADR-0011](0011-asn1-x509-cms-foundations.md) builds this decoding on the `der` 0.7 generation of the RustCrypto crates. Two defects of that generation were found while building `sigillum-testpki` (#30).

- **`der` 0.7.10 allocates a declared length before checking it.** `Reader::read_vec` (`src/reader.rs`, lines 138 to 142) allocates a primitive's declared length, then checks it against the input. It decodes owned values, such as an INTEGER. A few bytes of input can then request hundreds of megabytes.
- **`const-oid` 0.9.6 mishandles large arcs in dotted form.** Its parser of the dotted text form has three faults. The panic and the overflow are public through [RustCrypto/formats#1585](https://github.com/RustCrypto/formats/issues/1585) and [RustCrypto/formats#1592](https://github.com/RustCrypto/formats/pull/1592). They were fixed on master by [RustCrypto/formats#1592](https://github.com/RustCrypto/formats/pull/1592) and [RustCrypto/formats#1600](https://github.com/RustCrypto/formats/pull/1600). The wrong encoding was fixed on master by [RustCrypto/formats#1753](https://github.com/RustCrypto/formats/pull/1753). For an arc of 2^28 or more that fits in 32 bits, `ObjectIdentifier::new` can succeed. For example, `1.2.1111111111` gives the bytes `2A 84 91 E8 EB 47`. Displaying it or iterating its arcs then panics in every build (`src/arcs.rs`, line 109). Other such arcs are encoded wrongly without any error: `1.2.268435456` gives `1.2.0`. For an arc beyond 32 bits, the parser overflows (`src/parser.rs`, line 56). This panics where overflow checks are enabled, as in fuzz builds. Release builds wrap silently, so `1.2.4294967301` gives `1.2.5`. The fuzz target `tsa_input` of `sigillum-testpki` found the overflow.

`const-oid` 0.9.6 also has a defect in the DER form, public through [RustCrypto/formats#2412](https://github.com/RustCrypto/formats/pull/2412), which fixed it on master. It can silently truncate an arc that does not fit in 32 bits, instead of refusing it (`src/arcs.rs`, lines 79 to 83). This happens for an arc of five octets whose last octet is below 0x10. Other arcs beyond 32 bits are refused. Some valid arcs of 2^28 or more are refused too: `2A 8F FF FF FF 7F`, the arc 2^32 - 1, gives `ArcTooBig`. The arcs and dotted form of an identifier decoded from DER can therefore differ from those encoded. For example, the contents `2A 90 80 80 80 05` give `1.2.5`. The identifier keeps the encoded bytes, and its equality compares them (`src/lib.rs`, line 80). A comparison with a known identifier is therefore not affected. The truncation is silent, so fuzzing cannot detect it.

`sigillum-testpki` already guards against the first defect. Its function `timestamp::input::check_der` reads the identifier and length octets of every value, to a fixed nesting depth. It refuses any length that runs past its parent or the input. It borrows the input and allocates nothing. The clauses it cites, 8.1.2 and 8.1.3 of ITU-T X.690, were checked against the [02/2021 edition](https://www.itu.int/rec/T-REC-X.690-202102-I/en). It avoids the second defect by comparing object identifiers as text with the few it accepts, without parsing them.

`tools/dss-oracle` has another walk, `CertificateListBounds`, in Java. It predicts which CRLs DSS 6.5.1 can use. It therefore accepts indefinite lengths and does not check the outermost length. It also tolerates lengths that run past the input by up to the size of the CRL. It cannot be called from Rust, and its tolerances would defeat the rule below.

[ADR-0017](0017-defensive-api-rules.md), rule 8, already bounds the size of fetched responses. It does not cover documents and signatures that the caller passes directly, nor the structures nested inside them.

## Decision

These rules apply to every library crate that decodes untrusted input. They do not apply to the test tooling, which [ADR-0014](0014-test-pki-and-corpus.md) and the threat model leave outside the library.

1. **Input size limit.** Every public decoding entry point enforces an input size limit. The limit has a documented default and is configurable by the caller. As threat P2 requires, it stays within a documented maximum. Longer input is refused with a typed error before any decoding.
2. **Length walk before decoding.** An allocation-free walk runs before every decoding of DER from untrusted bytes. This includes each value encapsulated in the contents of a primitive, such as an OCTET STRING or BIT STRING, before that value is decoded. Examples are `extnValue`, `eContent` with the encapsulated `TSTInfo`, and the `response` of OCSP `responseBytes`. `subjectPublicKey` is one where the algorithm defines DER contents, such as an RSA key. Elliptic-curve and Ed25519 keys carry raw points. The walk checks every declared length against the bytes it is given. At every level of nesting, a length must fit in the bytes that remain in its parent and in the input. The walk also bounds the nesting depth. The depth limit has a documented default and is configurable within a documented maximum, as threat P2 asks. It is written from ITU-T X.690 (02/2021) only. It reads the identifier octets of clause 8.1.2 and the length octets of clause 8.1.3. Lengths take the definite form that clause 10.1 requires of DER. It refuses the indefinite form, a length that runs past its parent or the input, and bytes after the outermost value. It has two implementation limits, as `check_der` has today. It refuses a length with more than four subsequent octets, and a tag number of more than four octets. It leaves other length encodings longer than the minimum to the decoder. `der` 0.7.10 refuses them (`src/length.rs`, lines 229 to 234). Apart from the object identifier checks of rule 4, it does not judge the contents, which the decoder then checks. A format may allow data after the value, such as the zero padding of threat D10. For it, the walk module returns the length of the leading value. The end of the value is then found through the walk itself, not by an unchecked header read. Only the value is decoded.
3. **One shared walk in `sigillum-pki`.** The walk is a small, documented public module of `sigillum-pki`. Every crate that decodes DER already reaches `sigillum-pki` in the planned graph of [architecture.md](../architecture.md): `sigillum-cms`, `sigillum-jades` and `sigillum-ffi` directly, `sigillum-cades` and `sigillum-pades` through `sigillum-cms`. `sigillum-pdf` does not decode DER. No new crate enters the graph, but new direct dependency edges do. A crate that uses the module declares a direct dependency on `sigillum-pki`, for example `sigillum-cades` and `sigillum-pades`. The graph in architecture.md gains these edges when the module is first used. `check_der` moves from `sigillum-testpki` to this module in the first story that decodes untrusted input in a library crate. `sigillum-testpki` then uses the module, as a tooling crate may depend on a library crate. The Java walk of `tools/dss-oracle` is not reused, for the reasons given above.
4. **Object identifiers.** Object identifiers from untrusted input are parsed only through paths covered by a fuzz target. Fuzzing can reveal the panics described above, but not the silent wrong values, so the following rules apply.
   1. **General rule.** An untrusted object identifier, in dotted text or in DER, yields INDETERMINATE with "not supported" ([ADR-0007](0007-asymmetric-scope.md)) when it fails any of these:
      - the canonical syntax of sub-rule 2;
      - the limit of 2^28 on every arc;
      - parsing by `const-oid`, which applies only to encodings that the walk found well formed;
      - the round-trip check of sub-rule 5.
   2. **Canonical syntax of dotted text.** This includes `urn:oid:` values in JAdES. The text must meet all of these:
      - digits and single dots only, with no leading zeros, no empty arcs and at least two arcs;
      - a first arc of 0, 1 or 2, and a second arc below 40 when the first is 0 or 1 ([ITU-T X.660 (07/2011)](https://www.itu.int/rec/T-REC-X.660-201107-I/en), clause 7.6);
      - every arc below 2^28;
      - a documented maximum number of arcs.

      Arcs without leading zeros are the form of an integer-valued Unicode label, as X.660 (07/2011), clause 3.5.4, defines it.
   3. **Own encoder for dotted text.** sigillum encodes dotted text into DER contents octets with a small encoder of its own. It is written from ITU-T X.690 (02/2021), clause 8.19, only. The encoder's contents octets are wrapped in tag 6 and a length, then pass the walk. `from_bytes` then receives the contents octets. `const-oid` thus receives untrusted object identifiers only as DER, after the walk. Its textual parser is never used on untrusted input. The reason is the [RustCrypto/formats#1520](https://github.com/RustCrypto/formats/issues/1520) family of defects in its encoder from text, described below. They affect arcs that real enterprise identifiers use. Decoding the same arcs from DER is correct: `2A 81 00` gives `1.2.128`. The encoder is tested differentially against the walk, and a fuzz target includes it.
   4. **DER contents.** The walk of rule 2 also checks the contents of every value with the universal tag of OBJECT IDENTIFIER, number 6. No subidentifier may start with the octet 0x80 (X.690 (02/2021), clause 8.19.2). No subidentifier may have more than four octets, which keeps every arc below 2^28. This extends `check_der` as it is moved. The walk also refuses empty contents and a last subidentifier whose bit 8 is set (X.690 (02/2021), clauses 8.19.2 and 8.19.3). An object identifier has at least two components ([ITU-T X.680 (02/2021)](https://www.itu.int/rec/T-REC-X.680-202102-I/en), clause 32.11, note), so its contents are never empty. These three cases, a leading 0x80 octet included, are malformed DER. An arc of 2^28 or more yields INDETERMINATE with "not supported". The typed error of the walk module tells the two cases apart. The walk does not know the schema, so it checks only values with universal tag 6. An object identifier can also appear under an implicit tag. An example is `registeredID` in a GeneralName, `[8]` in [RFC 5280](https://www.rfc-editor.org/rfc/rfc5280), section 4.2.1.6, implicit under the module of Appendix A.2. GeneralName appears in certificates, CRLs and OCSP responses. The decoding code applies the same content check to such a value before it is used.
   5. **Round trip.** For dotted text, the dotted form that `const-oid` produces from the encoded value must equal the input exactly. For DER, the own encoder applied to that dotted form must give the contents octets again. This also covers defects beyond the known ones.
   6. **Comparison.** Where a value only needs to be compared with known identifiers, it is compared by its encoding, without formatting it or iterating its arcs. The identifier keeps its encoded bytes and its equality compares them.
   7. **Fuzzing.** Every fuzz target formats and iterates every object identifier it parses, so that the panics above surface.

   The known cases are these.
   - **The [RustCrypto/formats#1520](https://github.com/RustCrypto/formats/issues/1520) family.** In `const-oid` 0.9.6, the encoder from text miscodes the arcs 128, 16384 to 16511, and 2^21 to 2^21 + 16383 (`src/encoder.rs`, line 119). For example, `1.2.128` gives `1.2.0`. Only the encoding from text is affected. [RustCrypto/formats#1522](https://github.com/RustCrypto/formats/pull/1522) fixed it on master. The own encoder of sub-rule 3 avoids it.
   - **Structural limits of `const-oid` 0.9.6.** The DER contents must hold 3 to 39 octets (`src/lib.rs`, lines 92 and 143 to 147). The first octet must encode a first arc of at most 2 and a second arc of at most 39. The second limit applies under root 2 as well (`src/arcs.rs`, lines 124 to 130 and 157 to 160). So `1.2.3`, with two contents octets, and `2.999.3` are not supported. The documented length limit is therefore 39 contents octets.
   - **Arcs of 2^28 or more,** the faults described in the context.

   Arcs of 2^28 or more are an intentional restriction, recorded as DIV-2 in [divergences.md](../divergences.md) under class 3 of [ADR-0019](0019-divergence-classes-and-intentional-restrictions.md). An identifier such as `2.25` followed by a UUID is therefore not supported. The limit also guards against the truncation in the DER form. It is lifted only when a `const-oid` release used by sigillum contains all five fixes: [RustCrypto/formats#1522](https://github.com/RustCrypto/formats/pull/1522), [RustCrypto/formats#1592](https://github.com/RustCrypto/formats/pull/1592), [RustCrypto/formats#1600](https://github.com/RustCrypto/formats/pull/1600), [RustCrypto/formats#1753](https://github.com/RustCrypto/formats/pull/1753) and [RustCrypto/formats#2412](https://github.com/RustCrypto/formats/pull/2412). This applies to the DER path and to the limit of sub-rule 2 on the dotted path alike. Lifting it relaxes the four-octet rule for subidentifiers in sub-rule 4. It also relaxes the arc limit of the dotted syntax in sub-rule 2. The syntax and round-trip checks stay.
5. **Fuzz targets.** Every public decoding entry point has a fuzz target, which runs the size limit, the walk and the decoding together.

Once the walk passes on the bytes being decoded, no declared length in them exceeds those bytes. Each copy of contents is then at most their length. Values at one level of nesting do not overlap, and nested owned values copy their contents again at each level. Assume the decoder copies each value's contents at most once. The bytes copied by one decoding then total at most the depth limit plus one, times the length decoded. Each encapsulated value is a separate decoding with its own bound. The schema fixes the number of encapsulation levels. Decoded structures add a fixed overhead per element on top of the copied bytes.

The migration to the `der` 0.8 generation (#21) checks these defects, and records whether these rules can be relaxed. In particular, it checks whether the `const-oid` release of that generation contains all the fixes listed in rule 4. Only then can the limit of 2^28 on arcs be lifted.

## Alternatives considered

| Option | Advantages | Disadvantages |
| --- | --- | --- |
| Rely on `der` 0.7 alone | No extra code | A few bytes can request hundreds of megabytes, against threat P2 and objective O3 |
| Input size limit only | Simple; bounds the input | A small input can still declare a length far beyond itself, so allocations are not bounded by the input |
| Patch `der` 0.7 or wait for an upstream fix | Fixes the cause for every user | A patched fork in a security library; no fix is announced for the 0.7 generation, which [ADR-0020](0020-accepted-advisories-der-0-7.md) already treats as temporary |
| Move to the `der` 0.8 generation now (#21) | May remove the defects | The reasons of ADR-0011 for the 0.7 generation still hold, and the fixes there are not yet verified |
| A walk in each library crate | No shared module | Duplicated code, which can drift apart |
| A separate published crate for the walk | No dependency on `sigillum-pki` for the walk | Another crate name to protect (threat S5); its releases must be coordinated with the other crates; an extra public API to keep stable |
| Reuse `CertificateListBounds` | Already exists, citing X.690 | Java, and its tolerances for DSS defeat the purpose |
| Parse object identifiers with `const-oid` 0.9.6 alone, under fuzzing | No restriction on arcs; no extra code | Fuzzing cannot detect the silent wrong values; wrong identifiers could drive decisions |
| Parse dotted text with the textual parser of `const-oid` 0.9.6, with the syntax and round-trip checks | No own encoder | The round trip refuses the arcs of the RustCrypto/formats#1520 family, which real enterprise identifiers use |
| Chosen for dotted text: an own encoder from dotted text to DER contents, then `const-oid` on DER only | Arcs of the #1520 family are supported; one path into `const-oid`, after the walk | A small encoder to write, test against the walk and fuzz |
| Rules above, with the walk in `sigillum-pki` | Each allocation bounded by the bytes decoded; one implementation, fuzzed once and reused; no new crate | A second pass over the input, and one more for each encapsulated value; a small public module in `sigillum-pki`; new direct dependency edges to it; object identifiers with an arc of 2^28 or more are not supported until the defects are fixed |

## Consequences

The first story that decodes untrusted input in a library crate adds the walk module to `sigillum-pki`. It moves `check_der` and its tests there, and makes `sigillum-testpki` use it. The fixed depth of `check_der`, `MAX_DER_DEPTH` of 32, becomes a configurable depth limit with a documented default and maximum. Every decoding of DER from untrusted bytes, including each encapsulated value, runs the walk first. The walk gains the checks of OBJECT IDENTIFIER contents of rule 4. The decoding code applies the same check to object identifiers under implicit tags, such as `registeredID`. The general rule of rule 4 applies to both paths. So the first story that parses untrusted object identifiers, in either form, writes the own encoder. A story that reads only DER needs it too, because the DER round trip of sub-rule 5 applies the own encoder. In practice it is the first story that decodes untrusted DER. The encoder is tested against the walk. The same story adds the syntax and round-trip checks, and a fixture for DIV-2. Every public decoding entry point carries a size limit in its API, documented in rustdoc with its default and maximum. Every such entry point has a fuzz target. The review checklist of [quality-gates.md](../../development/quality-gates.md) refers to this ADR. The migration to the `der` 0.8 generation (#21) checks these defects. It also checks whether its `const-oid` release contains every fix that lifting the limit of 2^28 requires.

## Notes

- **2026-10-27.** [ADR-0025](0025-build-phase-1-on-der-0-8.md), rule 5, keeps `sigillum-testpki` on the `der` 0.7 generation and free of any dependency on a library crate. `check_der` therefore does not move, and `sigillum-testpki` keeps its own walk. The library gets its own walk module in `sigillum-pki`, written from ITU-T X.690 (02/2021). This replaces the last sentences of rule 3 and the sentences of the Consequences that move `check_der` and its tests and make `sigillum-testpki` use the module. The walk of rule 3 is therefore shared by the library crates only, not with the test tooling. The extension in rule 4.4, "This extends `check_der` as it is moved", and the checks the Consequences add to the walk apply to the library walk only. A differential test in `sigillum-oracle` runs the two walks over the same inputs. It compares only the structural checks: the identifier octets (a truncated tag, a tag number of more than four octets), the length octets (the indefinite form, more than four subsequent octets, a length past its parent or the input), the nesting depth and trailing data. The library walk runs in whole-input mode, not in the mode of rule 2 that returns the length of a leading value, and with the fixed depth limit of 32 of `sigillum-testpki`. The expected differences, the object identifier content checks of ADR-0024, rule 4, and the configurable depth, are mapped explicitly. The walk of `sigillum-testpki` stays as it is. The other rules stay in force. `const-oid` 0.10.2, the release of the 0.8 generation, does not contain [RustCrypto/formats#2412](https://github.com/RustCrypto/formats/pull/2412), so the limit of 2^28 on arcs remains. This note does not change the record above.
